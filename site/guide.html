Using Waterfall

Syntax, supplied lemmas, search modes and resource limits.

Lake dependency

With this checkout in a sibling directory, a Lean project can use the following dependency in lakefile.toml. Both projects need the same toolchain, leanprover/lean4:v4.33.1.

[[require]]
name = "waterfall"
path = "../Waterfall"

After lake update, import Waterfall makes the tactics available. Waterfall 0.1 targets Lean 4.33.1; compatibility is also tested on Lean 4.30.0. This candidate is in a private GitHub repository. Public installation and Reservoir coordinates will be documented after release.

Definitions and lemmas

import Waterfall

namespace Example
def append : List Nat → List Nat → List Nat
  | [], ys => ys
  | x :: xs, ys => x :: append xs ys

example (xs : List Nat) : append xs [] = xs := by
  waterfall [append]
end Example

Local hypotheses and relevant definitions from the current module are considered automatically. The bracketed list supplies imported definitions and helper lemmas.

The Lean tutorial is compiled by the test suite. The Software Foundations examples cover expression optimization, insertion sort and tree traversal. Waterfall also applies to remaining branches after manual introductions or induction.

Registered views and data witnesses

Both modes use registered Lean induction and case eliminators, as well as local functions that return data. Raw case analysis remains available. Backward constructor application can propose one constructor layer for an implicit data argument, then infer its fields or leave them as obligations. Arbitrary nested witness synthesis is outside this small fallback.

Search modes

waterfall (mode := .search) (effort := 3000)
waterfall (mode := .committed) (effort := 3000)

The default search backtracks through a complete continuation, including sibling goals. Its iterative schedule explores increasing structural depth and solver strength.

Committed mode tries ordinary work across the agenda before induction and commits after the first local progress. It can restore the original conjecture once per trial. It retries earlier goals after a sibling changes shared witnesses. It prunes alternatives, so extra effort cannot recover every path it discards.

Resource limits

effort counts dispatched operations, including failed attempts and charged checkpoint restarts. Enumeration and ordering consume time and heartbeats but are not separate attempts. More effort funds deeper plans and stronger operations.

Lean's enclosing maxHeartbeats and maxRecDepth still apply. The finer attemptHeartbeats option is in raw heartbeats; Lean's maxHeartbeats option is in thousands of raw heartbeats. An operation's slice grows with strength and never exceeds the enclosing remaining allowance.

Parallel execution

waterfall (cpus := 4) (effort := 3000)

This explores different trials of the same policy concurrently. The tactic uses dedicated worker threads; operating-system CPU affinity may further limit concurrency. Workers share total budgets. The first complete proof wins; fixed-budget coverage and timing can differ from the sequential default.

Proof scripts

waterfall? offers a checked “Try this” hint. Accepting the hint replaces the invocation with ordinary Lean proof commands. Both search modes and the CPU option are supported. If a step cannot be rendered as a tactic, the replacement uses an explicit proof term, which can be longer. Checking the replacement takes additional time.

(report := true) enables printed search statistics.

The optional Waterfall.Observe import provides internal timing, action recording and checked-plan replay. Its interfaces are described in the reference and tested examples.
