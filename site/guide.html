Using Waterfall

The tactic works on the current goal, including goals left by a partly manual proof. This example supplies a recursive definition explicitly:

import Waterfall

namespace Example
def append : List Nat → List Nat → List Nat
  | [], ys => ys
  | x :: xs, ys => x :: append xs ys

example (xs : List Nat) : append xs [] = xs := by
  waterfall [append]
end Example

The bracketed arguments can be definitions or theorems. Local hypotheses are available automatically. Waterfall also looks for definitions from the current module; it does not unfold every imported definition.

Other examples appear in the Lean tutorial and the Software Foundations proofs.

Proof scripts

waterfall? runs the same search and prints a “Try this” hint containing a replacement script. Lean checks that script before offering it. The script can still contain simp_all or grind; it records the successful route through the proof rather than every failed attempt.

Some steps are printed as explicit proof terms when tactic syntax is unavailable. These hints can be long. Producing and checking a hint also takes time beyond the search itself.

Search modes

waterfall (mode := .search) (effort := 3000)
waterfall (mode := .committed) (effort := 3000)

.search is the default. It keeps alternatives until all subgoals have been proved. Backtracking restores the whole proof state, including shared witnesses. For example, a witness that solves one premise may have to be abandoned because it makes another premise impossible.

.committed accepts the first step that makes local progress and discards the alternatives. It tries non-inductive work across the remaining goals before choosing an induction. Once per trial, it can return to the original conjecture before induction. Extra effort does not recover alternatives that this policy discards.

Effort and time limits

effort counts attempted proof operations and charged restarts. Failed attempts count too. Candidate generation and ordering take time and heartbeats but do not count as separate attempts.

The search runs trials with different limits on proof depth and solver strength. A larger effort budget lets it reach more trials. This can find a proof sooner if a stronger operation succeeds quickly, or take longer because more failed paths are explored.

attemptHeartbeats sets the base limit for one operation in raw heartbeats; trial strength scales it. Lean’s maxHeartbeats option uses thousands of raw heartbeats. Each operation is also bounded by the enclosing remaining allowance. maxRecDepth remains a separate Lean limit.

Parallel execution

waterfall (cpus := 4) (effort := 3000)

This runs depth/strength trials on at most four dedicated workers. They share the attempt budget and divide the remaining heartbeat budget. The first complete proof wins; other workers are cancelled and joined before the tactic returns.

The default is one worker. Parallel runs may find different proofs within the same budget. CPU affinity can limit concurrency further.

Diagnostics

(report := true) prints search statistics. The optional Waterfall.Observe module records per-operation timing and the successful proof plan. Its API also supports replay without search.

Installation

A project can depend on a sibling Waterfall checkout through lakefile.toml:

[[require]]
name = "waterfall"
path = "../Waterfall"

Both projects need the same lean-toolchain. After lake update, the tactic is available through import Waterfall. The release information lists the supported versions and repository.
